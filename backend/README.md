# Архитектура проекта

Серверная часть данного проекта реализуется в виде **модульного монолита** с использованием
**гексагональной архитектуры**.

В проекте будут применяться осознанные компромиссы (shortcut'ы) для создания наиболее гибкого и поддерживаемого
кода. В некоторых местах будет целенаправленное отступление от правил "Чистой архитектуры" R.Martin.

Допускается использование аннотаций Spring в application слое: аннотации объявления бинов и аннотации Spring AOP для
уменьшения количества бойлерплейт кода, использование других инвазивных средств фреймворков/библиотек(например
классы/интерфейсы и тд) или аннотаций других библиотек в ядре приложения не разрешается для поддержания чистого кода и
чистой архитектуры.

В будущем возможны миграции на другие фреймворки (например Quarkus, переход на Spring Data JPA и тд), и использование
Kotlin для написания других модулей из-за чего структура проекта должен быть наиболее гибкой для безболезнненых
переходов.

# Общая структура

В проекте используется **"выразительная структура"** пакетов.

Проект разделен по bounded context (бизнес функциям), которые являются корневыми пакетами. Внутри них лежат
adapter,domain,application пакеты согласно гексагональной архитектуре.

Помимо bounded context пакетов, выделяются также:

- Common - содержит общий код используемый сразу в нескольких модулях;
- Infrastructure - содержит инфраструктурный код который относится ко всем модулям.

## Разбиение на пакеты/подпакеты:

- Domain. Содержит чистые доменные модели и их Value classes. Разделяется на подпакеты по принципу: один пакет на каждую
  доменную модель с ее Value classes если модели сложные или их много. В иных случаях используется плоская структура;


- Application Содержит бизнес логику. Состоит из:

    - Service. Содержит классы сервисы (use-case) и их внутренние модели (если имеются). Разбиваются на под-пакеты по
      функциям (функция в данном контексте - группа тесно связанных между собой use-case).

    - Port. Определяет порты для взаимодействия ядра приложения с внешним кодом или вызовом внешним кодом ядра
      приложения (Под ядром понимается application и domain слои) Состоит из:
        - In. Содержит входящие порты - Use case (их интерфейсы и модели), которые вызываются внешним кодом. Делятся
          по пакетам - по функциям/доменным моделям в зависимости от количества классов в пакете. При разделении по
          доменным моделям идет разделение внутри них на command и query use-case (Разделение по доменным моделям
          происходит при большом количестве use-case'ов). Модели используемые портами располагаются в том же пакете что
          и сами порты.
        - Out. Содержит исходящие порты для взаимодействия ядра приложения с адаптерами. Разбивается на подпакеты по
          концепциям: persistence, crypto, и тд. Если классов в подпакетах много - идет разбиение на более мелкие пакеты
          по функциям/доменным сущностям;
- Adapters. Являются реализацией портов. Состоят из:
    - In. Адаптеры вызывающие ядро приложения. Разбиваются по технологиям (Например web, Mq и тд) и внутри данных
      пакетов по функциям.
    - Out. Адаптеры вызываемые ядром приложения. Разбиваются на подпакеты по технологиям (Например Db, Kafka и тд) и
      внутри по функциям/сущностям.

## Стратегии маппинга между слоями:

- Для Input adapter -> application используется маппинг в объекты ядра вместе с маппингом в value objects для плоских
  dto (для того чтобы перевести их в value objects и напрямую использовать в ядре приложения). Для сложных или глубоко
  вложенных объектов маппинг не используется. В таком случае входные данные напрямую десерелизуются в input объекты
  ядра, которые объявлены в port.in, все приведения к value object и доменным классам производятся в самом ядре
  приложения

  **Случаи когда необходимо выделить input модель в адаптере:**

    - Есть разные точки входа в один use-case (Например Kafka и Http);
    - Модель для use-case собирается из разных источников (Например cookie,request body и тд);
    - В модели много инфраструктурных/библиотечных деталей;

  Тогда выделяется отдельная модель для веб адаптеров и для application слоя (в application слое модель будет иметь
  функцию самовалидации).

  **Случаи когда необходимо выделить output модель в адаптере:**

    - Нужно сокрытие/уменьшение количества полей возвращаемых из use-cas'а;
    - Один и тот же use-case вызывается разными input адаптерами и каждый должен возвращать разный набор полей;
    - Необходимость в инфраструктурных/библиотечных деталях в модели;

  Тогда выделяется отдельная output модель в адаптере.

- Для Application -> Out adapter всегда (за исключением Query операций) если нужен маппинг используется two-way
  mapping (Общение между application и out
  adapter происходит через передачу объектов application/domain моделей и адаптер сам их маппит в нужные ему модели и
  возвращает обратно объект application/domain модели);

## Использование Shortcut'ов:

Для уменьшения количества boilerplate кода, используются следующие shortcut'ы:

- Если действия над доменной моделью являются обычными CRUD операциями или небольшими логически связанными операциями,
  можно создать общий для данных операций сервис класс и общий out - порт для взаимодействия с бд. Но если появляется
  больше бизнес логики то данная операция сразу выносится как отдельный use-case, идет разбиение используемых портов и
  тд. согласно общей структуре проекта

- Для операций чтения применяется паттерн CQRS: Создается общий сервис класс, и общий use-case с требуемыми для чтения
  моделями. Сервис класс выполняет проверку прав и других параметров и проксирование к адаптеру бд, который сразу внутри
  себя выполняет поиск нужных данных с помощью SQL с использованием No-mapping стратегии (Пришедшие данные сразу
  десерелизуются в нужную модель). Данный подход позволяет исключить ненужный маппинг между слоями, и проксировать
  запрос минуя ненужные при чтении бизнес-валидации и маппинги.
