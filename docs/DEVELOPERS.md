## Разработчикам:

### Структура проекта:

* `master` - содержит production-ready код, готовый к разворачиванию
* `dev` - ветка разработки. Содержит готовые фичи, необходима для синхронизации бекенда и фронтенда. Прямые пуши в `dev`
  и
  `master` **запрещены**
* `feat,fix,refactor` ветки - создаются от dev ветки, для изменения кода

### Именование веток:

При изменении кода необходимо создать новую ветку от ветки dev. Название задается по следующему шаблону:

**`направление(backend/frontend) / Тип(feat/fix/refactor) / имя(если несколько слов - разделение с помощью нижнего
подчеркивания)`**

Пример: *backend/feat/implements_users_chat*

### Flow-разработки:

1) Создание ветки от dev для конкретной задачи. Пример последовательности действий:
    - git checkout dev
    - git pull origin dev
    - git checkout -b frontend(backend)/feat(fix,refactor)/название_задачи

2) После завершения разработки, необходимо выполнить локальную кода линтерами и прочими инструментами контроля качества,
   описанными в READMI.md для [backend](../backend/README.md) и [frontend](../backend/README.md), иначе сборка не
   пройдет этапы CI GitHub Actions

3) Создание Pull Request:
    - При завершении работы запушьте свою ветку на GitHub и создайте Pull Request в ветку dev.
    - Влияние кода в dev возможно только после успешного прохождения всех автоматических проверок CI (сборка, линтеры,
      тесты).

4) Работа с секретами и переменными окружения:
    - Строго запрещено хардкодить пароли, ключи API и токены в коде или конфигурационных файлах (application.yml, .js и
      т.д.).
    - Все секреты должны передаваться через переменные окружения в локальном файле .env (файл находится в
      .gitignore).
    - При добавлении новой переменной окружения в проект разработчик обязан добавить её ключ (с пустым или тестовым
      значением) в шаблонный файл .env.example
