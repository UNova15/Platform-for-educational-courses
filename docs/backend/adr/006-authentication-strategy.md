# Выбор стратегии аутентификации

* Статус: Accepted
* Дата: 01.03.2026

## Контекст и Проблема

Необходимо выполнять аутентификацию пользователей при их входе/регистрации в системе. Не аутентифицированный
пользователь будет иметь общую роль - [пользователь](../FR.md), после входа/регистрации пользователь будет иметь
логическую роль Преподаватель в своих курсах и роль Студент при записи на другие курсы.
Стратегия аутентификации должна быть безопасной и удобной для пользователей.

## Рассмотренные варианты

* Jwt + Refresh token
* Form login
* OAuth2.0
* Http Basic Authentication

## Решение

Был выбран вариант Jwt + Refresh token. Данный вариант достаточно удобный для пользователя т.к. даже после длительного
отсутствия активности пользователя он сможет войти в приложение с помощью Refresh токена не проходя заново процесс
входа/регистрации. Данный способ аутентификации достаточно безопасный и быстрый т.к. JWT будет нести всю нужную
информацию о пользователе для его аутентификации (то есть не нужно делать вызов к бд для его проверки), сам JWT
подделать невозможно благодаря использованию механизма подписи, что делает использование JWT быстрым и безопасным.
Ощутимый минус JWT - сложность инвалидации (например заблокировали пользователя), но это можно решить с помощью создания
Black list (например в Valkey). JWT будут короткоживущими токенами, а Refresh - долгоживущими, хранящимися в бд в
зашифрованном виде. Клиент будет хранить в Cookie refresh токен и отправлять его на специальный эндпоинт для перевыпуска
Jwt и refresh токенов.

JWT токен будет возвращаться в теле ответа и храниться на клиенте in-memory для защиты от CSRF-атак, а Refresh
Token будет передаваться в HttpOnly Cookie для защиты от XSS-атак

В дальнейшем возможна интеграция OAuth2.0 от сторонних провайдеров (например Google) для упрощения пользователям входа в
систему.

## Последствия

* **Плюсы:**
    * Безопасность
    * Скорость
* **Минусы / Риски:**
    * Сложности при инвалидации Jwt токенов
