# Выбор способа хранения аутентификационных сессий

* Статус: Accepted
* Дата: 22.11.2026

## Контекст и Проблема

Необходимо выбрать способ хранения сессий аутентификации пользователей для выполнения требований описанных в Use-case'ах
регистрации, аутентификации и смены пароля. Необходимо хранить количество оставшихся попыток ввода кода, контролировать
ttl и дать возможность повторной отправки кода с сбросом ttl и количеством попыток.

## Рассмотренные варианты

* Хранение в PostgreSQL
* Использование Key-Value DB (Valkey)
* Хранение в локальном кеше (Java code/Caffeine и тд)

## Решение

Был выбран вариант хранения в Valkey.

Необходимо было иметь возможность контроля TTL что Valkey умеет по умолчанию, также будут частые операции чтения и
перезаписи, что принесло бы дополнительную нагрузку на основную бд. При использовании основной бд пришлось бы
реализовывать логику статусов аккаунтов т.к. регистрация/сброс пароля имеют 2 шага: ввод данных и ввод кода
подтверждения из-за чего необходимо было бы вводить статусы аккаунтов (Подтвержден/Неподтвержден) что загрязнило бы и
усложнило логику. Также Valkey (или другой подобный кеш) необходимо будет использовать в будующем в люом случае из-за
оптимизации запросов на чтение бд (т.к. проект является heavy-read) и необходима возможность PUB/SUB для будующей
синхронизации веб-сокетов.

## Последствия

* **Плюсы:**
    * Удобный механизм для сохранения аутентификационных сессий
    * В будущем проще оптимизировать чтение бд, синхронизировать веб-сокеты т.к. конфигурация Valkey в проекте уже есть
* **Минусы / Риски:**
    * Необходимость изменения настроек инфраструктуры
    * Новая, мало изученная технология
