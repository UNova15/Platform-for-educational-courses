# Выбор системной архитектуры

* Статус: Accepted
* Дата: 01.03.2026

## Контекст и Проблема

В данный момент над проектом работает 1 Бекенд разработчик, из-за чего архитектура должна быть легко поддерживаемой и
легко масшатбируемой в будущем. Архитектура не должна приносить много дополнительных расходов на поддержку
инфраструктурного кода и общей настройки инфраструктуры.

## Рассмотренные варианты архитектуры проекта:

* Микросервисная архитектура
* Модульный монолит
* Монолит

## Решение

Был выбран модульный монолит.

Модульный монолит упростит разделение проекта в будущем на
микросервисы (что необходимо для масштабирования).В данный момент модульный монолит позволяет легко писать код, при этом
не приносит
больших затрат как временных, так и финансовых на поддержание отдельных сервисов и их связи между собой. При
использовании модульного монолита модули будут реализовываться как отдельные Maven модули состоящие из 2х частей: API и
Impl, что позволит исключить возможность использования внутренних частей одного модуля внутри другого (Обеспечение
инкапсуляции в процессе разработки). Для межмодульного взаимодействия будет использоваться модуль API, который содержит
нужные интерфейсы/классы для взаимодействия с модулем к которому он относится. В дальнейшем, при разделении монолита на
микросервисы, модули API будут превращены в SDK для взаимодействия с данными сервисами.
Каждый модуль будет иметь свою отдельную схему в бд для упрощения разделения на микросервисы в будущем и предотвращения
использования межмодульного взаимодействия в бд (Каждый модуль должен иметь доступ только к своей схеме в бд). Прямые
ссылки (FK) между таблицами из разных схем запрещены для простого разделения на разные сервисы (у каждого сервиса будет
своя независимая бд). Ссылочная целостность обеспечивается логикой приложения.

## Последствия

* **Плюсы:**
    * Поддерживаемая, масштабируемая, архитектура приложения, с небольшими затратами на ее поддержание
* **Минусы / Риски:**
    * Повышение сложности проекта
    * Отсутствие FK между схемами переносит ответственность за ссылочную целостность на код приложения
    * Сложность в написании транзакционных сценариев, затрагивающих несколько модулей одновременно.
