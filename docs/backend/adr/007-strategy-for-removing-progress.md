# Стратегия удаления прогресса

* Статус: Accepted
* Дата: 19.10.2026

## Контекст и Проблема

Как описано в [Удаление тестов](../FR.md#удаление-тестов) и [Удаление уроков](../FR.md#удаление-уроков) и аналогичном
изменении уроков/тестов в FR будет производится удаление прогресса у пользователей которые прошли данный урок/тест.
Такое решение было принято обеспечения справедливости и равенства для всех пользователей в рамках курса (кто прошел и
кто не прошел урок/тест) т.к. при изменении урока/теста количество вопросов/содержание может сильно изменится поэтому
единственным справедливым решением для всех пользователей будет удаление прогресса тех, кто прошел старую версию. Но
возможно наличие большого числа записей прогресса из-за чего удаление может занять большую часть времени. Также удаление
прогресса должно происходить атомарно с удалением/изменением урока или теста т.к. в ином случае тест или урок будет
изменен а прогресс либо останется либо будет удален только у части пользователей, что приведет данные в неконсестентное
состояние.

## Рассмотренные варианты

* Изменение или удаление урока/теста и удаление прогресса в рамках одной транзакции БД в виде прямого вызова API модуля
  прогресса
* Использование асинхронного удаления в фоновом потоке в виде прямого вызова API модуля прогресса
* Создание внутреннего события удаления после успешного коммита транзакции изменения/удаления теста или урока, которое
  будет обрабатывать модуль прогресса
* Создание внутреннего события удаления и его обработка в модуле прогресс в рамках одной общей транзакции

## Решение

Был выбран вариант: Создание внутреннего события удаления и его обработка в модуле прогресс в рамках одной общей
транзакции. При таком подходе в модульном монолите сохранится принцип низкой связности (Low coupling) т.к. модули не
вызывают напрямую API друг друга в данном случае а используют события. Использование общей транзакции будет
гарантировать атомарность данной операции (То есть удаление/изменение теста или урока произойдет в той же транзакции что
и удаление прогресса). Данный вариант самый подходящий для модульного монолита. В дальнейшем, при разделении проекта на
микросервисы будет использоваться тот же принцип с событиями, но уже отправляемыми в MQ (с возможным использованием
Transactional Outbox для гарантии доставки). На текущем этапе проекта
с [текущей нагрузкой](../NFR.md#1-емкость-и-нагрузка) удаление даже нескольких тысяч записей в одной транзакции не будет
являться тяжелой или медленной операцией.

## Последствия

* **Плюсы:**
    * Сохранение низкой связности модулей
    * Строгая консистентность
* **Минусы / Риски:**
    * При дальнейшем росте проекта возможны проблемы из-за пессимистичной блокировки большого количества записей
      прогресса и рост нагрузки на бд при удалении всех этих записей
    * Рост времени на обработку запроса при росте числа записей прогресса
