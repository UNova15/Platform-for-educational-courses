# Нефункциональные требования

### 1) Емкость и нагрузка:

+ Аудитория: 100.000 зарегистрированных пользователей, 10.000 ежедневно активных пользователей
+ Read/Write соотношение: 10:1
+ Peak RPS: 150. 135 - read, 15 - write операций. Система является heavy - read
+ Рост данных: 10 Тб/год. Основную часть размеру будут составлять Файлы и видео контента уроков

### 2) Производительность:

+ Read latency: 95 перцентиль времени ответа API на операции чтения не должен превышать 200 мс
+ Write latency: 95 перцентиль времени ответа API на операции записи/изменения состояния не должен превышать 500 мс.
+ Тяжелые операции будут выполняться асинхронно в фоне.
+ Пагинация обязательна для методов API, потенциально способных вернуть более 100 элементов - максимум 50 элементов за
  запрос.

### 3) Доступность и Отказоустойчивость:

+ SLA - 99.9%
+ Масштабируемость: Бекенд-приложение должно быть Stateless, чтобы обеспечить горизонтальное автомасштабирование при
  превышении нагрузки на CPU > 70%.

### 4) Восстановление:

+ RTO: До 2 часов
+ RPO: До 15 минут

### 5) Согласованность данных:

+ Строгая согласованность для операций изменения курса, прогресса, а также для каскадного удаления прогресса при
  изменении уроков (в рамках одной БД-транзакции). Переход на Eventual Consistency планируется только при выделении
  модулей в микросервисы

### 6) Безопасность:

+ Пароли хранятся исключительно в виде хэшей. Алгоритм хеширования - Bcrypt.
+ Персональные данные (email, ФИО) не должны попадать в application-логи системы.
+ Взаимодействие между клиентом и сервером только по TLS 1.2+ (HTTPS).

# Ограничения

### 1) Стек технологий: Java 25, Spring fraemwork, возможно использование Kotlin

### 2) Использование монолитной модульной архитектуры на старте проекта

### 3) Реляционная СУБД в качестве основного хранилища, S3 для хранения файлов и видео

### 4) Использование JWT + Refresh tokens для аутентификации пользователей
