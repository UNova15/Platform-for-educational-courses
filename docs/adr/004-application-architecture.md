# Выбор архитектуры приложения

* Статус: Accepted
* Дата: 01.03.2026

## Контекст и Проблема

Проект планируется развивать как минимум в течении 2х лет из-за чего архитектура проекта должна позволять легко его
дорабатывать и развивать. Посколько в предыдущем adr был
выбран [модульный монолит](003-choice-of-system-architecture.md) выбранная архитектура будет распространятся сразу на
все приложение. Проект должен быть легко поддерживаемым с точки зрения изменения функциональных требований и
нефункциональных. Проект должен быть готовым к масштабированию на большие нагрузки без переписывания
кодовой базы на другой стек и без сильного изменения архитектуры.

## Рассмотренные варианты

* Гексагональная
* Слоевая

## Решение

Была выбрана гексагональная архитектура.

Для обеспечения возможности поддерживаемости кода и обеспечения чистого кода будет использована Гексагональная
архитектура. Это позволит легко заменять зависимости которые могут меняться по мере развития проекта.
В течении жизни проекта не исключается переход на другие фреймворки/библиотеки (Например использование Spring Data JPA
или переход на Kotlin и Ktor или использование Quarkus). Гексагональная архитектура позволит писать чистый, легко
развиваемый и поддерживаемый код. Будут некоторые накладные расходы на ее поддерживание, но они будут сведены к минимуму
благодаря рациональному использованию shortcut'ов, в результате чего получится чистый и поддерживаемый код с
минимальными
накладными расходами на его поддержание. В ядре приложения будет использовать DDD подход, что будет хорошо сочетаться с
гексагональной архитектурой т.к. гексагональная архитектура избавит application слой от внешних зависимостей и откроет
возможность использования DDD.

## Использование shortcut'ов:

* Допускается использование аннотаций Spring в application слое: аннотации объявления бинов и аннотации Spring AOP для
  уменьшения количества бойлерплейт кода, использование других инвазивных средств фреймворков/библиотек(например
  классы/интерфейсы и тд) или аннотаций других библиотек в ядре приложения не разрешается для поддержания чистого кода и
  чистой архитектуры.

* Если действия над доменной моделью являются обычными CRUD операциями или небольшими логически связанными операциями,
  можно создать общий для данных операций сервис класс, общий out - порт для взаимодействия с бд. Но если появляется
  больше бизнес логики то данная операция сразу выносится как отдельный use-case, идет разбиение используемых портов и
  тд. согласно общей структуре проекта

* Для операций чтения применяется паттерн CQRS: Создается общий сервис класс, и общий use-case интерфейс с требуемыми
  для чтения моделями. Сервис класс выполняет проверку прав и других параметров и проксирует к адаптеру бд, который
  сразу внутри себя выполняет поиск нужных данных с помощью SQL с использованием No-mapping стратегии (Пришедшие данные
  сразу десерелизуются в нужную модель). Данный подход позволяет исключить ненужный маппинг между слоями, и проксировать
  запрос минуя ненужные при чтении бизнес-валидации и маппинги.

## Последствия

* **Плюсы:**
    * Поддерживаемая, масштабируемая, архитектура приложения, с небольшими затратами на ее поддержание
* **Минусы / Риски:**
    * Повышение сложности проекта
    * Необходимо писать множество тестов, особенно архитектурных для ее соблюдения
    * Увеличение количества бойлерплейт-кода (интерфейсы, порты, DTO)
